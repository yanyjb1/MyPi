## platform

### platform

#### 16. 系统识别与跨平台

平台这一层要能回答「这台机器是什么系统」，好让别处按系统决定做法。

- 一枚值：族（unix / windows）、名字（linux / macos / windows）、架构
- 落点一：配置的 bootstrap（`config/mod.rs` 写 `config.yaml` 那一步）按它挑缺省，
  Windows 上生成的与 Linux 上生成的不一样
- 落点二：将来工具的名单（Windows 上没有自带 shell，`bash` 这一个不该出现）

已经按 unix 写死的地方（各自单独立项，不在这条里）：

| 地方 | 写死的什么 | Windows 上 |
|---|---|---|
| 时区 | `/usr/share/zoneinfo`、`/etc/localtime` | 两个都没有，现在会掉回 UTC |
| bash 工具 | `setsid`、`kill`、`/bin/sh` | 没有自带 shell |
| 目录与环境 | `XDG_*`、`$HOME` | `%APPDATA%`、`%LOCALAPPDATA%`、`%USERPROFILE%` |
| 传输子进程收尾 | `kill -KILL` | 没有 kill（`taskkill` 也不是一回事） |
| 浏览器 | Helium / Chromium 的路径 | 路径形状全不一样 |

#### 40. Windows 命名管道

`platform::ipc` 的 Windows 侧全是 `unimplemented!()`（`bind` / `connect` / `accept` / `Read` /
`Write`），控制字段 `config.server.platform.ipc = pipe` 今天一按就崩。协议层（`src/ipc/`）一行都不用改。

- 标准库没有命名管道：要么手写 `kernel32` 的 FFI（`CreateNamedPipeW` / `ConnectNamedPipe`），

- 缝已经留好：`Cost::Pipe` 加 `platform::ipc` 的 `bind` / `connect` / `unlink` 三个函数，
  其中 `unlink` 在 Windows 上是空操作（管道名不是文件）。
- 验收要一台 Windows：ssh 上去起 server、跑前端、发一条消息、看退场与端点清理。

## tui

### tui（前端那一波）

#### 18. 补全重做（功能重做，渲染那块不动）

`tui/zone/main/reserved/completion/`（约 1400 行）现在的模型是错的：一枚标签
（`ArgKind` 那五档）说「候选从哪来」，前端拿到标签再自己 switch；一次只补光标下那一个词，
没有「级」这回事；候选来源散在前端（模型与档案由输入上下文捎进来，路径自己扫盘）；
`insert` 里塞的是整行，每处调用点自己知道怎么拼。作废的东西：`ArgKind` 五档、
`CommandInfo.args` 那个字符串、四路 switch、`leaf.rs` 的叶子判定。

新模型：候选是一棵树，一次问一层。

- 一枚候选 = 值 + 说明 + 一枚「还有下一级」的布尔
- 这一级打满（输入的字符串与某个候选一致）之后看那枚布尔：有下一级再问一层，
  没有就当补全完成
- 这一级没有候选 = 空列表，弹窗不开
- 「这一级该给什么」由声明说（契约里那条命令的参数描述，服务端命令与前端自有命令
  都在同一张表里）：路径那一段前端自己扫，名单那几段（模型、档案）问服务端一次拿回来，
  命令名从契约那张表来
- 那两份名单在前端**初始化**的时候拿一次（`Call::Pools`），之后补全全程本地
- 前端只负责画与下钻；渲染那一块不重做，只换喂给它的形状
- **接线另算**：渲染那块现在读的字段（`name` / `hits` / `is_dir` / `insert`）会后对不上，
  把新形状接上去这件事记在这里，别把它和渲染重构混成一件事

#### 19. 前端要有一条展示队列（预加载那一类）

前端得有个优先级：给用户看的部分先画完；那些「不管用户接下来做什么、都要默默做完」的事
（预加载，比如初始化时拿两份名单、预热路径），排在后面慢慢做，不许挡住画面。

#### 24. 前端初始化时读工作目录

今天前后端同一个进程，**工作目录由前端自己读**（服务端不去猜）；服务端的工具环境等它给。

日后拆成两个进程时：前端会有一个特殊事件叫**初始化**，初始化过程中它读当前工作目录，
并**把新会话要的几样值一起备齐**——目录、模型（用户没换就用配置里的默认）、名字、档案。
这些值**随首条用户消息**一起交上去；服务端收到之后才完成工具环境的初始化、才写入。

**命令不建会话**：首条消息之前用户敲的 `/switch` `/name` `/profile` 由前端自己拿着，
不上交、不落库；消息才是创建会话的触发器。不然一条命令开一个会话，resume 时满屏幽灵会话。

没有新会话就没有工具调用，也就不用装工具环境。

落点：`agent/loop/env.rs::build`（工具环境在首条消息到达时才建）。

#### 44. 清单怎么算、怎么优化（前端留字眼，后端照它起算）

**现状**

`api/call/todo.rs` 把这条会话**所有**回合的块读出来，挑出 `todo` 的调用，用工具
本尊按顺序重放一遍，得到那一瞬间的清单。触发时机两处：进会话读一次；之后只要有 `todo` 的结果
落盘，再读一次（`session/ingest.rs` 的 `Follow::Todo`）。

**重难点**

代价随会话长度长——读一次要扫全部块；todo 密集的一轮里，每落一批就重扫一次。

**待办**

给重放一个起点，不必从会话开头算。

- 字眼：清单被清空时，在那次移除操作的**结果块的 `memo` 栏**里记一句「本轮清单已清空」。
- 谁判：前端。后端不做渲染性的计算，也不越界指挥。前端跟着增量走（`todo` 的请求与结果都在
  它收到的块里），算到每一条都消失了，才去 post。
- post：前端第一次算出「正在用清单」→ post 一次「在用」（**只 post 一次**）；算到最后一条被
  移除 → post 一次「用完」，**带上那次移除的调用编号**。
- 时机：块号只在**落盘那一批**里出现——转发是即时的（`Relay::Tail`，不带
  块号），落盘是攒批的（`Relay::Blocks`，带块号），每 `batchTools` 个工具回合一批（默认 10），
  外加回合结束与用户消息各落一次。所以前端算到「清单空了」的那一瞬间，手上只有调用编号；要指块，
  得等那批落盘之后，用调用编号对上块号，再 post。
- 后端：照块号把字眼写进那一块的 `memo`。
- 重放那侧：遇到这个字眼就把账清零，并把起点挪到这里——它前面的回合不用再重放。

| 缺的 | 现在有什么 | 要加什么 |
|---|---|---|
| post 带调用编号 | `Post::Rewind` 就带块号，形状现成 | 新加一个 post 变体（在用 / 用完 + 调用编号） |
| 按调用编号找块 | 块表有 `call_id` 列，请求块与结果块各带一份 | 查的时候要加「类型 = 工具结果」，并确认它在这条会话的列表里 |
| 落开关、写 memo | `sessions.todo_on` 这一列在，**全仓没有写入者**；改一个已落盘块的 `memo` 也没有路径 | 一个写入者，加一条跨请求改 `memo` 的写路径 |

**尚未解决**

1. 这个字眼是事后补写的：前端没开、或者没算到最后一条，就没人写它。所以重放不能依赖它，
   只能拿它当加速与起点；没有它照样要算得对。
2. 那个读口现在以 `todo_on` 为门（关着就回空清单）。开关改由前端驱动之后，从没被前端打开过的
   会话会读到空清单——这层含义要一起定清楚。
