# 说明
fs/file service是一套针对代码编辑提供的工具，它主要包含以下套件：
1. read
2. grep
3. edit/splice（互斥）
4. write

由于至多同时启用四件工具，因此，将本系列工具别称为四件套。同时，由于用户个人的偏好，以下及此处的四件套仅指代启用splice的四件套。

设计时主要以rust/单库为目标，也就是，指定工作区内的rs文件修改+fmt格式化+cargo check通过+cargo test（暂未实现）+git commit提交改动的场景，做专门优化，以期以此，在不给模型bash权限的前提下，令模型能完成正常代码改动的全部工作。同时，因为没有不可控的bash权限，git本身的兜底已经足够，亦即，仅启用本套工具时，本harness不需要专门设计沙箱。

理论上，任何一门编程语言，只肖有确定的文件后缀、语法分析器（亦即关键行开闭判定），格式化、检查、测试支持，即可由四件套接管。目前来看，静态编译型语言最适合四件套的模式，其中，按照适配程度与优化可能并结合用户个人偏好，分为如下几个级别：

1. T0（原生、最完善）Rust
2. T1（理论上完全适配）Go Zig Swift
3. T2（不用折腾）C# Java Kotlin
4. T3（特定条件下可以做）
    1. C/CPP（仓库必须采用现代 CMake 或 Ninja 构建，并提前生成包含完整头文件路径与宏定义的 compile_commands.json 编译数据库，以此驱动 clang-format 与 clang-check）
    2. Python（本项目直接内置ruff，或者要求用户仓库中内置ruff，ruff可以充当语法格式化+checker，语法切片再对py特有的括号深度与缩进栈蒸一下就好）
5. T4（不太可能，不抱希望）Ruby Lua
6. T5（死一边去，本项目永远不支持）JS/TS/PHP

文档语言，亦即非编程语言，也可以纳入这种框架，但只有语法分析，不提供检查等功能。

支持计划：rust Markdown（已经基本实现） python -> web三件套（html/htm css 原生js） -> go，其它的，反正我也不用，留给社区吧（如果可能的话）。=-=

四件套彼此之间配合与git联动如下：
read：给出目标目录的路标，亦即枢纽视图，方便模型了解该区域（即该目录）功能的内外往来。也就是，在read目录时，就让模型站在这个区域的十字路口上，方便模型了解数据和功能的流向。
grep：根据关键字，迅速定位到目标建筑，同时支持X-ray（例如A::b），以关系型的定位，方便模型迅速定位到相关代码，提供lavish开关方便模型自主选择升档以获取更多上下文。
splice（edit&write同理，只是无关行号漂移的特殊处理）：通过仅行号/行号+首词的方式，匹配目标行，而后进行修改，修改后进行语法格式化（在这一步进行尽量宽松的检查，只要不是写入错误，比如多了一个花括号导致直接语法崩溃无法解析，就允许写入，warn之后再修），而后进行检查，如果有测试标记，那么触发对应的单体测试，除了语法格式化这一步可能阻止模型写入，其它部分仅替模型检查/测试并整理结果，亦即，尽量给模型自由，不干涉其发挥。
同时，通过config.server.agent.tools.addEdits::bool来判定，是否在模型每次改动后即刻提交改动，由于模型在仅启用四件套时没有bash权限，因此也不需要做沙盒。同时，配置项addEdits为真时，write允许模型写一个特殊的改动，即：`.commitmessage`，写进这个文件的内容将被视为提交的信息，由harness自动完成。

# 原则

1. 给目标语言做支持的原则：
    语法检查器、类型检查器、测试等，仅采用rust生态提供的目标语言支持器（形同ruff/ty之于py），或者该语言自身生态内部提供的支持，例如，不采用node生态为py提供的支持。
2. 有限支持。
    即使是rust也有让人一眼摸不着脑袋的逆天写法，所以，只对最常见的场景做支持，不太常见的情况要做出取舍，但是对于我们决定支持的部分，既然支持了，就做到最好。
