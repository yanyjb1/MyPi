# 设计说明

## 工具定位

`fs/file service` 是专为受控代码与文本编辑设计的基础工具集，最多同时启用以下四项工具（简称“四件套”）：

1. `read`：文件与目录阅读器
2. `grep`：全局/局部检索引擎与关系雷达
3. `edit` / `splice`（互斥）：精确局部编辑与批量行级编辑（本设计文档默认以启用 `splice` 为基准）
4. `write`：整文件创建、覆写与提交触发器

## 设计哲学

1. 无沙箱可控闭环：在仅启用四件套、不开放 bash 权限的前提下，通过“受控局部编辑 + 语法门禁 + 自动体检 + Git 原子提交”完成全部开发闭环。因为不存在不可控的外部命令执行，Git 历史本身即构成完整兜底，无需额外设计进程沙箱。
2. 充分自由与最小干涉：除语法解析崩溃（会导致文件结构损坏无法解析）外，不阻断模型的编辑操作；所有静态检查与单元测试结果仅作结构化整理并随回执反馈给模型，交由模型自主决策后续修复。

## 协同工作流

### 1. `read`：十字路口与结构地图

1. 目录视图（枢纽视图 / Hub）：读取目录时，不仅列出文件清单，还聚合该区域的核心模块暴露接口（`exports`）、向下管辖子单元（`down`）、对外依赖（`out`）以及被外部引用的上游入口（`up`），让模型一进入目录便站在功能与数据流向的“十字路口”。
2. 文件视图（大纲索引 / Table）：读取单文件时，依据对应语言的词法/结构扫描器提取关键起止行号（函数、类、控制流块、配置节、章节标题等），降低大文件阅读成本，并为后续 `splice` 提供精确行号坐标。

### 2. `grep`：关键字定位与多语言 X-ray 雷达

1. 快速建筑定位：基于关键字在工作区范围内快速检索匹配行，提供 `lavish` 开关供模型自主升档获取更宽上下文。
2. 多语言混合 X-ray 关系透视（Relations）：
    1. 自动按检索范围内的文件所属语言分组执行关系扫描，支持多语言混血仓库并行检索；
    2. 支持各语言特色的关系查询语法（如 Rust 的 `A::b`、Python/Kotlin 的 `A.b`、原生 Web 三件套的跨文件 `#id` / `.class` 锚点透视）。

### 3. 编辑套件（`splice` / `edit` / `write`）：行号稳定编辑与延迟格式化机制

为消除“每次局部修改后立即重排代码导致后续编辑行号漂移”，并替代模型频繁手动调用外部格式化命令的低效行为，编辑套件采用 “编辑期零漂移校验 + 提交期统一格式化” 的两阶段流水线：

1. 编辑写入
    1. 语法门禁（只验不改），调用对应语言的格式化/解析器在内存中执行干跑语法校验（Dry-run Syntax Gate）。
    2. 若代码存在严重语法崩溃（如括号不匹配导致解析器无法构建语法树），阻断本次写入并返回精确报错行号
2. 自动体检与按需测试：
    1. 静态检查（`check`）：写入落盘后，静默运行对应语言的静态检查器，将报错与修复建议整理为结构化 `Fault` 随回执返回（不阻断流程）；
    2. 定向单测（`test`）：若改动范围命中包含测试标记（如 Rust 的 `#[test]`）的代码块，自动提取测试名称并触发精确单体测试，整理结果返回。
3. 提交收尾：
    1. 通过 `config.server.agent.tools.addEdits::bool` 控制自动提交行为：
        - true时每当编辑操作落盘，自动暂存。
        - false时，仅当写入虚拟文件时才暂存。
    2. 虚拟提交：允许模型通过 `write` 工具写入特殊虚拟文件 `.commitmessage`。此时：
        1. 语法格式化本次提交的所有文件；
        2. 将`.commitmessage` 的内容作为 Commit Message 完成 Git 提交。

删除文件：仅`write`支持，文件内容设置为`__DELETE_FILE__`，则解释为删除对应文件。

提交、删除、格式化、以上支持仅在模型无Shell时提供，其余时候由模型通过shell命令完成。

## 语言支持矩阵

### 支持原则

1. 工具正统。
    1. 语法检查器（形同rustfmt之于Rust）、语义检查器（形同cargo check之于Rust）、测试（形同cargo test之于Rust）等，仅采用rust生态提供的目标语言支持（形同ruff/ty之于py），或者该语言自身生态内部提供的支持。
    2. 在Rust生态和目标语言生态同时提供语法检查器支持时，优先使用rust生态的支持（性能+助力Rust生态）。
2. 有限支持。
    即使是rust也有让人一眼摸不着脑袋的逆天写法，所以，只对最常见/最通用的场景做支持，不太常见的情况要做出取舍，但是对于我们决定支持的部分，既然支持了，就做到最好。
3. 多语言。
    现代仓库基本都是混血的，不能粗暴地假定目标仓库就只有一种语言。

### 支持矩阵与路线

> 理论上，任何一门文件只要有确定的后缀、结构切片规则以及对应的校验能力，即可由四件套接管。依据文件在仓库中的语义角色与交互深度，纳入支持的语言划分为以下三类：

#### 1. 编程语言

具备完整的模块依赖树、符号引用关系与可执行语义，开启六槽满配能力（结构大纲、模块依赖图、X-ray 关系透视、语法门禁与提交期统一格式化、静态检查、命中范围的单体测试）。按适配程度与偏好分级：

1. T0（原生、最完善）：Rust（已支持）
2. T1（理论上完全适配）：Go（已支持）、Zig（计划中）、Swift（无计划）
3. T2（按需支持、不用折腾）：Kotlin（计划中）、Java 17+/21+ LTS（计划中）、Smali（计划中）、C# 8+（无计划）
4. T3（特定条件下可以做）：
  1. Python（已支持）
  2. Web 三件套：HTML/HTM、CSS、原生 JS（已支持）
  3. C / CPP（已支持）
  4. R（已支持）
  5. POSIX Shell：bash/zsh（计划中）
5. T4（不太可能，不抱希望）：Ruby、Lua（动态元编程过重，静态结构与依赖图收益极低）
6. T5（永不支持，死一边去）：现代重型前端框架与动态 Web 生态（TS、React、Vue、PHP 等）；后缀多义性语言（.m、.v、.pl，缺少确定解释器）；远古脚本（.bat/.cmd）

#### 2. 数据与配置语言

面向机器解析或系统配置，无函数调用与模块依赖树（无需 hub、relations 与 test），但语法容错率为零，写错标点即导致解析崩溃，配置结构大纲切片、语法门禁、校验与提交期统一格式化：

1. JSON（已支持）
2. TOML（已支持）
3. YAML（已支持）
4. XML（已支持）
5. JSONC / JSON5（计划中）
6. SQL：PostgreSQL / SQLite（计划中）

#### 3. 文档语言

面向人类阅读的散文与知识库，不存在阻断写入的语法错误（格式化、静态检查与单测置空），核心价值在于长文档的结构导航与知识网络联动：

1. Markdown（已支持）
2. Typst（计划中）
